# 16 路 640×480@30FPS 多通道视频写 DDR 架构设计

## 1. 文档目标

本文针对当前多路视频采集系统中的 DDR 写入瓶颈进行架构分析，并设计一套面向：

- 16 路视频输入
- 640×480
- RGB888
- 30 FPS
- AXI4 256 bit
- AXI Clock = 100 MHz

的高可靠、多通道视频写 DDR 架构。

设计目标不是单纯提高理论带宽，而是解决当前系统中由于：

- 长 burst 独占
- burst 内数据断流
- 多通道 Head-of-Line Blocking
- B Response 阻塞调度
- FIFO 服务延迟过长

所导致的局部 FIFO overflow。

最终目标是实现：

> 16 路视频并发采集，在存在 AXI backpressure、DDR 短时停顿及其他 master 竞争时，仍能稳定、无溢出地写入 DDR。

---

# 2. 系统带宽分析

## 2.1 单路视频数据量

输入格式：

```text
640 × 480
RGB888 = 3 Byte/pixel
30 FPS
```

单帧数据量：

\[
640\times480\times3
=921600 Byte
\]

即：

```text
900 KiB/frame
```

单路带宽：

\[
921600\times30
=27,648,000 Byte/s
\]

约：

```text
27.65 MB/s
```

---

## 2.2 16 路总带宽

\[
27.648\times16
=442.368 MB/s
\]

即约：

```text
442 MB/s
```

---

## 2.3 AXI 理论带宽

AXI：

```text
256 bit = 32 Byte
100 MHz
```

因此：

\[
32\times100M
=3.2GB/s
\]

视频流占理论 AXI 带宽：

\[
\frac{442.368}{3200}
\approx13.82\%
\]

因此：

> **16 路视频采集并不存在总线理论带宽不足的问题。**

即使考虑 AXI arbitration、DDR refresh、Gemmini DMA、framebuffer 等额外流量，视频采集本身的平均写带宽仍然相对有限。

# 3. 当前架构

当前系统可抽象为：

```text
Camera0 ─ FIFO0 ─ Writer0 ─┐
Camera1 ─ FIFO1 ─ Writer1 ─┤
Camera2 ─ FIFO2 ─ Writer2 ─┤
                           │
          ...              ├── AXI Arbiter ── AXI4 ── DDR
                           │
Camera15 ─FIFO15─Writer15 ─┘
```

每个 channel writer 可以一次申请：

```text
64 AXI beats
```

每个 AXI beat：

```text
256 bit = 32 Byte
```

因此一个 burst：

\[
64\times32=2048B
\]

即：

```text
2 KiB
```

---

# 4. 当前问题的根本原因

## 4.1 Camera 数据产生速度与 AXI burst 消耗速度不一致

Camera tap：

```text
2 pixel/tap
```

RGB888：

```text
2 × 3B = 6B/tap
```

产生一个 AXI beat：

```text
32B
```

需要：

\[
32/6\approx5.33
\]

次有效 tap。

64 beat 则需要：

\[
64\times32/6
\approx341.3
\]

次有效 tap。

需要特别注意：

> 这里的 341 是 **有效数据 tap 数量**，并不一定等于 341 个 AXI wall-clock cycles。

如果视频存在：

- HBlank
- VBlank
- tap_valid 间隔
- CDC stall
- pipeline bubble

真实时间可能明显大于 341 个 AXI cycle。

---

# 5. 当前最大的问题：过早占有 AXI W Channel

当前行为本质类似：

```text
FIFO 有少量数据
      │
      ▼
请求 64-beat burst
      │
      ▼
AWLEN = 63
      │
      ▼
获得 AXI Writer
      │
      ▼

W0
等待 Camera 数据
等待
等待

W1
等待
等待

W2
...

W63

      │
      ▼
burst 完成
```

问题是：

> 一个 transaction 已经开始，但 transaction 所需的完整数据并没有准备好。

因此产生：

```text
AXI WREADY = 1

但是

AXI WVALID = 0
```

此时物理 AXI 通道是空闲的。

但是因为当前 burst 尚未结束：

```text
其他 Camera 无法使用 W Channel
```

---

# 6. AXI4 为什么不能直接切换其他通道

AXI4 与 AXI3 一个非常关键的区别是：

> AXI4 Write Data Channel 没有 WID。

所以不能：

```text
CH0 W0

CH0 暂时没有数据

CH1 W0
CH1 W1

CH0 W1
```

这种 transaction 内 W 数据 interleave 是不允许的。

因此一旦启动：

```text
AWLEN = 63
```

当前 master 就必须按照对应 transaction 顺序完成：

```text
W0
W1
...
W63
WLAST
```

之后才能切换到其他 write transaction 的数据。

所以：

> 如果启动 burst 时 source FIFO 还没有准备好整个 burst，W Channel 就可能被这个 producer 长时间绑死。

---

# 7. 问题本质：Head-of-Line Blocking

假设：

```text
CH0 FIFO 数据不足
CH1 FIFO 很满
CH2 FIFO 很满
CH3 FIFO 接近 overflow
```

但是当前：

```text
Owner = CH0
```

结果：

```text
                AXI
                 │
                 ▼

CH0 ───── WVALID=0

CH1 ───── READY DATA
CH2 ───── READY DATA
CH3 ───── READY DATA
```

总线：

```text
WREADY = 1
```

却没有数据传输。

这属于典型的：

# Head-of-Line Blocking

即：

> 排在最前面的 transaction 阻塞了后面实际上已经准备好的 transaction。

---

# 8. 为什么 16 路下问题明显恶化

如果一个 channel 的 64-beat burst 需要约：

```text
341 valid taps
```

那么后面的 channel 理论上可能经历：

```text
15 × 341
≈ 5115 valid-tap service interval
```

实际 wall-clock 等待时间还可能更长。

因此：

```text
CH0 service

CH1 wait

CH2 wait

...

CH15 wait
```

等待期间 CH15 的 FIFO 仍持续接收 Camera 数据。

只要：

\[
Arrival > Service
\]

持续足够时间：

```text
FIFO → FULL → OVERFLOW
```

因此系统虽然：

```text
AXI 使用率很低
```

却依然：

```text
Camera FIFO Overflow
```

这也是整个问题最关键的矛盾。

---

# 9. 为什么“一次只抓一路”能够工作

当前 workaround：

```text
只使能一个 Camera
```

实际上相当于：

```text
一个 producer
    │
    ▼
一个 writer
    │
    ▼
AXI
```

系统不存在：

```text
其他通道等待当前 owner
```

所以即使当前 burst 内存在：

```text
WVALID bubble
```

也不会导致其他 Camera FIFO overflow。

因此：

> “一次抓一路”并没有解决 AXI writer 的效率问题，而是通过消除竞争掩盖了调度问题。

# 10. 新架构的核心思想

新架构需要将：

```text
Camera 数据产生时序
```

和：

```text
AXI DDR transaction 时序
```

彻底解耦。

核心原则为：

> **先准备数据，再申请 AXI。**

而不是：

> 一边等 Camera 数据，一边占用 AXI。

目标结构：

```text
Camera Stream
     │
     ▼
Pixel Packer
     │
     ▼
Elastic FIFO
     │
     │ 数据达到一个完整 burst
     ▼
Burst Ready
     │
     ▼
Multi-channel Scheduler
     │
     ▼
AXI Write Engine
     │
     ▼
Continuous W Transfer
     │
     ▼
DDR
```

# 12. Channel Capture Frontend

每个 Camera 独立拥有：

```text
Camera
  │
  ▼
RGB888 Capture
  │
  ▼
Byte/Beat Packer
  │
  ▼
256-bit FIFO
```

建议 FIFO 中直接保存：

```text
256-bit AXI beat
```

而不是保存：

```text
2 pixel / entry
```

这样 scheduler 看到的 FIFO occupancy 单位统一为：

```text
AXI beat
```

避免后面进行：

```text
pixel
→ byte
→ beat
→ burst
```

多层换算。

---

# 13. RGB888 → 256-bit Packer

输入：

```text
2 pixels = 6 Byte
```

输出：

```text
256 bit = 32 Byte
```

由于：

```text
32B
```

不是：

```text
6B
```

的整数倍，因此需要 byte accumulator。

例如：

```text
Tap0   +6B
Tap1   +6B
Tap2   +6B
Tap3   +6B
Tap4   +6B
----------------
        30B

Tap5   +6B
----------------
前2B补完 Beat0
剩4B进入 Beat1
```

因此 packer 内部应该维护：

```text
byte_count
partial_data
```

形成完整 32 Byte 后：

```text
fifo_push
```

---

# 14. 一个非常有利的条件

单帧 RGB888：

\[
640\times480\times3
=921600B
\]

而：

\[
921600/32
=28800
\]

即：

```text
28800 AXI beats / frame
```

同时：

\[
921600/512=1800
\]

所以如果使用：

```text
16 beat burst
```

每个 burst：

```text
16 × 32B = 512B
```

则一帧恰好：

```text
1800 bursts
```

没有 frame tail。

同样：

```text
32 beats = 1 KiB
```

一帧：

```text
900 bursts
```

而：

```text
64 beats = 2 KiB
```

一帧：

```text
450 bursts
```

也是整数。

因此，如果 framebuffer 使用：

```text
linear contiguous frame
```

则非常适合固定 burst DMA。

# 15. 推荐 Burst 长度

第一版建议：

# 16 beats

即：

```text
512 Byte / burst
```

原因不是 AXI 传输效率最高，而是综合：

- arbitration latency
- fairness
- FIFO occupancy
- DDR efficiency
- 多 Camera 并发

之后的平衡点。

---

# 16. Burst 长度比较

100 MHz 下，一个 AXI clock：

```text
10 ns
```

如果 WREADY 始终为 1：

| Burst | Bytes | 单次 W Channel 占用 |
|---:|---:|---:|
| 8 beats | 256 B | 80 ns |
| 16 beats | 512 B | 160 ns |
| 32 beats | 1024 B | 320 ns |
| 64 beats | 2048 B | 640 ns |

16 路全部 ready 时，某一路等待前面 15 路：

### 16 beats

\[
15\times160ns
=2.4\mu s
\]

### 32 beats

\[
15\times320ns
=4.8\mu s
\]

### 64 beats

\[
15\times640ns
=9.6\mu s
\]

因此：

> 16 beat 可以显著缩短 worst-case service latency。

# 17. 关键改造：Full-Burst-Ready

一个 channel 只有在：

```text
fifo_count >= burst_len
```

时才能进入 scheduler。

例如：

```text
burst_len = 16
```

则：

```text
fifo_count >= 16 AXI beats
```

之后才能：

```text
request = 1
```

禁止：

```text
FIFO 有 1 beat
↓
直接申请 16/64 beat transaction
```

应该变成：

```text
FIFO：

Beat1

...
Beat15

        ▼

        │
        ▼
AW
        │
        ▼

```

如果：



必须增加：

```text
active_mask[15:0]
```

例如当前只有 8 路：

```text
active_mask =
```

scheduler 只考虑：

```text

    active_mask[ch]
```

# 22. Round-Robin Arbitration

正常情况下采用：

```text
Round-Robin
```

例如：

```text
CH0
 ↓
CH1
 ↓
CH2
 ↓
...
CH15
 ↓
CH0
```

优点：

- 公平
- 实现简单
- latency 有上限
- 不会永久 starvation

# 23. 仅 Round-Robin 仍然不够

真实 DDR 会存在：

- refresh
- AXI stall
- Gemmini burst
- framebuffer traffic
- DDR bank conflict
- read/write turnaround

因此某些 Camera FIFO occupancy 可能突然变高。

所以应该增加：

# Watermark Priority

# 24. FIFO Watermark

建议定义：

```text
LOW
HIGH
CRITICAL
```

例如按 occupancy 百分比：

```text
LOW      = 25%
HIGH     = 75%
CRITICAL = 87.5%
```

具体值后续通过仿真调整。

状态：

```text
occupancy < HIGH
    NORMAL

occupancy >= HIGH
    URGENT

occupancy >= CRITICAL
    CRITICAL
```

# 25. Scheduler Priority

推荐：

```text
Priority 0:
CRITICAL channels

Priority 1:
HIGH channels

Priority 2:
Normal burst-ready channels
```

同一优先级内部：

```text
Round-Robin
```

最终：

```text
CRITICAL RR
   ↓
HIGH RR
   ↓
NORMAL RR
```

既保证：

```text
overflow protection
```

又保证：

```text
fairness
```

# 26. Aging 防止 Starvation

可以增加：

```text
wait_counter[ch]
```

每个 eligible channel：

```text
未被选中 → wait_counter++
```

达到阈值：

```text
AGE_THRESHOLD
```

之后提升 priority。

防止某一路长期被 urgent traffic 压制。

# 27. FIFO 深度建议

当前如果 FIFO 为：

```text
1024 × 6 Byte
```

则实际容量：

\[
6144B
\]

约：

```text
6 KiB/channel
```

平均视频数据率下：

\[
6144 / 27.648MB/s
\approx222\mu s
\]

所以平均意义上：

```text
6 KiB
```

其实并不小。

真正的问题是：

> 当前 AXI scheduler 能制造数十甚至数百微秒的 service latency。

如果资源允许，建议改成：

```text
256-bit × 256 entries
```

即：

```text
32B × 256
=8 KiB/channel
```

16 路总共：

```text
128 KiB
```

也可以进一步：

```text
512 entries
```

即：

```text
16 KiB/channel
```

16 路总计：

```text
256 KiB
```

推荐：

> FIFO depth 参数化。

例如：

```text
CHANNEL_FIFO_DEPTH = 256
```

第一阶段使用 8 KiB/channel。


# 30. AXI Write Engine 内部结构

建议：

```text
                    Descriptor FIFO
                          │
              ┌───────────┴───────────┐
              │                       │
              ▼                       ▼

              │                       │
```

# 31. 当前可能存在的另一个性能问题

如果当前行为是：

```text
AW
 ↓
W0...W63
 ↓
WLAST
 ↓
等待 BVALID
 ↓
释放 arbiter
```

则存在严重浪费。

B channel 表示：

```text
write completion response
```

并不意味着：

```text
W channel 必须一直等待 B
```

正确设计应该：

```text
CH0:

AW
W0
W1
...
WLAST
  │
  └────────────── scheduler 可以继续 CH1


CH1:

AW
W0
W1
...


之后：

B0
B1
```

所以：

> **调度器释放条件应该以 WLAST 为主，而不是等待 B Response。**

# 32. Write Outstanding

为了避免：

```text
DDR Response latency
```

降低 transaction throughput，可以允许多个 write transaction outstanding。

例如：

```text
MAX_OUTSTANDING = 4
```

第一版。

之后：

```text
8
```

进行 benchmark。

Tracker 保存：

```text
ID
channel
address
frame_id
status
```

---

# 33. Outstanding 注意事项

AXI4 的：

```text
AW channel
W channel
B channel
```

是解耦的。

但是 W data 不能像 AXI3 一样任意 interleave。

所以：

```text
AW0
AW1
AW2
```

可以提前发出。

但是 W 数据必须保持与对应 write transaction 的正确顺序关系。

因此建议使用：

```text
AW Descriptor Queue
```

维护：

```text
AW issuance order
```

W engine 严格按照 queue 顺序发送。

---

# 34. 第一版 Outstanding 不需要做得太激进

建议路线：

### V1

```text
一个 W transaction
多个 B outstanding
```

即：

```text
WLAST
↓
立即切换下一个 burst
```

但之前 burst 的 B 可以稍后回来。

这已经能够消除：

```text
B latency
```

造成的 scheduler stall。

### V2

再增加：

```text
AW pipelining
```

提前发下一个 transaction 的地址。

# 35. Adaptive Burst

第一版：

```text
固定 16 beats
```

最简单。

后期可以：

```text
Normal:
16 beats

High occupancy:
32 beats

Critical:
64 beats
```

但必须满足：

```text
完整 burst 已缓存
```

---

# 36. 更推荐的 Adaptive Burst 策略

不要仅根据当前 channel occupancy。

还要观察：

```text
other_urgent_present
```

例如：

```text
if fifo >= CRITICAL
   && no_other_critical:
       burst = 64

else if fifo >= HIGH
   && no_other_high:
       burst = 32

else:
       burst = 16
```

这样避免：

```text
为了快速排空一个 FIFO
```

重新产生：

```text
长 burst 阻塞其他高压通道
```

# 37. 地址生成

每路 Camera 维护：

```text
frame_base[ch]
```

# 38. AXI 4KB Boundary

AXI burst 不能跨：

```text
4 KiB boundary
```

所以 burst generator 必须满足：

```text
addr[11:0]
+
burst_bytes
<=
4096
```

通用计算：

```text
max_beats_before_4k =
(4096 - addr[11:0]) / 32
```

实际：

```text
burst_len =
min(
    target_burst,
    fifo_ready_beats,
    max_beats_before_4k
)
```

---

# 39. 当前图像尺寸恰好非常适合 4KB

一帧：

\[
921600/4096=225
\]

即：

```text
225 × 4 KiB
```

如果：

```text
frame_base 4 KiB aligned
```

并采用：

```text
continuous linear framebuffer
```

那么整个 RGB888 frame 恰好由：

```text
225 个 4 KiB block
```

组成。

这对 DMA 非常友好。

因此强烈建议：

```text
frame buffer
```

保持：

```text
contiguous linear layout
```

而不是人为制造不必要的 stride padding。

```text

```

# 41. QoS 原则

这些 master 的性质不同。

Camera Capture：

```text
实时性强
FIFO overflow 后数据不可恢复
```

Gemmini：

```text
吞吐敏感
但是短时 stall 通常不会造成数据错误
```

因此 QoS 原则应该：

> Camera 有最低带宽保证，Gemmini 使用剩余带宽。

而不是：

> Gemmini 长 burst 无限压制 Camera。

正常：

```text
Gemmini
Camera
Framebuffer

公平竞争
```

Camera FIFO 高水位：

```text
Camera Priority++
```

Critical：

```text
Camera Writer
   >
Gemmini
```

FIFO 恢复：

```text
恢复正常 QoS
```

因此属于：

# Dynamic QoS

而不是固定最高优先级。

# 59. 当前架构与新架构对比

| 项目 | 当前架构 | 新架构 |
|---|---|---|
| AXI Burst | 64 beat | 16 beat 起步 |
| Burst 启动 | 少量数据即可 | 完整 burst ready |
| Burst 内 WVALID | 存在大量空洞 | 连续发送 |
| 仲裁 | 长时间独占 | burst-level RR |
| B Response | 可能阻塞下一 transaction | 异步处理 |
| Camera 并发 | 一次一路更稳定 | 16 路并发 |
| FIFO | 被长 latency 消耗 | Elastic buffer |
| Priority | 普通 RR/固定 | Watermark QoS |
| Inactive Channel | 可能仍参与 | Active Mask |
| Write Outstanding | 弱或没有 | 4~8 |
| AXI 利用率 | 低且碎片化 | burst 化 |
| Gemmini 兼容 | 容易竞争 | 可扩展 QoS |

# 60. 架构核心变化

旧架构本质：

```text
Camera
 │
 │ producer timing
 ▼
AXI Writer
 │
 │
 ▼
DDR
```

Camera 数据产生速度直接决定：

```text
WVALID
```

所以 Camera stall 会直接变成：

```text
AXI stall
```

---

新架构：

```text
Camera
   │
   ▼
Elastic FIFO
   │
   │ decouple
   ▼
Scheduler
   │
   ▼
AXI Burst Engine
   │
   ▼
DDR
```

Camera：

```text
什么时候来数据
```

与 AXI：

```text
什么时候发送 burst
```

已经解耦。

这是整个架构中最重要的变化。

# 61. 最终判断

对于：

```text
16 × 640×480 RGB888 @30FPS
```

总视频写入只有：

```text
≈442 MB/s
```

而：

```text
AXI256 @100MHz
```

理论能力：

```text
3.2 GB/s
```

所以当前系统问题绝不是：

```text
DDR 带宽不足
```

而是：

```text
数据还没有准备完整
        ↓
过早获取 AXI transaction
        ↓
长 burst 被低速 producer 占有
        ↓
WVALID 出现大量 bubble
        ↓
后续 Camera 无法获得 W channel
        ↓
Head-of-Line Blocking
        ↓
FIFO Overflow
```

# 62. 最终推荐架构

本项目推荐最终采用：

```text
16 × Camera
       │
       ▼
16 × RGB888 → 256b Packer
       │
       ▼
16 × Elastic Beat FIFO
       │
       ▼
Full-Burst Ready
       │
       ▼
RR + Watermark + Aging Scheduler
       │
       ▼
16/32/64 Adaptive Burst
       │
       ▼
Descriptor FIFO
       │
       ▼
AXI AW/W Pipeline
       │
       ▼
WLAST Release
       │
       ├──────────────► next burst
       │
       ▼
Async B Response Tracker
       │
       ▼
DDR
```

其中第一阶段最关键的四项是：

```text
1. 16-beat burst

2. Full-Burst-Ready

3. burst 内连续 WVALID

4. WLAST 后立即切换 channel
```

如果这四项完成，当前系统从：

> “Camera producer 驱动 AXI 时序”

转变为：

> “Buffer + Scheduler 驱动 AXI 时序”。

这才是从 8 路扩展到 16 路时真正应该完成的架构升级。
