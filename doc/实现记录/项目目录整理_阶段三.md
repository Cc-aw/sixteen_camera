# 项目目录整理：第三阶段

本阶段将 `sw/src/` 的 63 个源码和头文件归入功能目录，保留根目录 `main.c`
作为程序入口。源码中的项目头文件统一使用相对 `sw/src/` 的明确路径，
例如 `platform/console.h`、`ai/runtime/ai_tensor_slot_pool.h`。

## 功能目录

| 目录 | 文件数 | 职责 |
| --- | ---: | --- |
| `sw/src/platform/` | 7 | 启动汇编、裸机运行库、控制台、地址定义、cache 操作 |
| `sw/src/board/` | 6 | 板级 GPIO、UART/trap、Xilinx 配置和 `xparameters.h` |
| `sw/src/video/` | 8 | 摄像头配置、摄像头状态、HDMI 和视频服务 |
| `sw/src/ai/runtime/` | 15 | 流式/批量调度、Tensor/Head Slot、推理运行时、输入控制 |
| `sw/src/ai/backend/` | 8 | 模型 ABI、YOLOv5nu / TinyYOLOv2 / GemCC / stub 适配 |
| `sw/src/ai/postprocess/` | 15 | PPU 队列、Head 发布、检测结果、标签和 overlay |
| `sw/src/diagnostics/` | 4 | 后处理与带宽诊断、YOLOv5nu 自检 |

`diagnostics/ai_postprocess_diag.c` 中仍有生产代码使用的 API，目录分类不表示
该文件可以从生产固件删除。TinyYOLOv2 使用的批量调度和预处理也继续保留。

逐文件对应关系见[阶段三软件目录迁移映射.json](阶段三软件目录迁移映射.json)。

## 构建和接口调整

- `sw/Makefile` 显式选择的生产源码集合保持一致，路径随目录迁移更新。
- 本地目标文件和 `.d` 依赖文件跟随源目录分层；启动目标改为
  `$(BUILD)/platform/startup.o`，避免旧 `startup.d` 引用已迁走的路径。
- 编译规则为每个目标创建父目录，支持并行构建。
- 项目代码保留 `-Isrc`；另以 `-Isrc/board` 满足 AMD BSP 固定使用
  `xparameters.h` 的要求，vendor 编译显式预包含 `board/xparameters.h`。
- Host tests 保留测试 MMIO stub 的搜索顺序，更新项目头文件与 C 文件路径。
- GemCC 可选 backend 的相对运行库引用、独立 Gemmini 构建及 smoke 构建入口同步更新。
- PPU 标签生成/测试脚本和非 README 文档中的源码路径同步更新。

模型目录、模型参数、生成器和历史软件快照保留。当前三路64继续使用
`sw/yolov5/dim16_dual/` 的运行实现，尚未对这个历史名称做迁移。
README 内容继续按要求保留，旧源码路径可查询本阶段映射。

## 使用

```bash
make firmware SOC_VARIANT=single4
make firmware SOC_VARIANT=dual16
make firmware SOC_VARIANT=triple64
make test-software
```

原 `make test-runtime` 仍可单独运行流式调度测试。硬件构建入口保持不变。

### 原有 TinyYOLOv2 链接问题

另外执行了 dual16 / TinyYOLOv2 完整构建。本地源码编译成功，但链接缺少：

```text
ai_batch_runtime_print_frame_profiles
ai_frame_snapshot_release
ai_frame_snapshot_acquire
```

已在临时目录用迁移前的 64 份源码/头文件、原 Makefile 和未修改的模型对象复现
相同错误。原 TinyYOLOv2 源清单没有包含 frame snapshot 实现，批量运行时也未提供
main 调用的 frame profiles 接口。本阶段保留原功能与源集合，将其记录为旧分支问题；
不将 TinyYOLOv2 完整固件标记为构建通过。

本次未下载固件、生成新比特流或进行板测；编译通过不表示运行性能或推理结果已重新验收。
