# PCLK / 视频系统时序重构：Codex 实施任务书

> 版本：v1.0 · 2026-09-05  
> 适用对象：`xcvu13p-fhga2104-2-i`，Vivado 2023.2，当前 8 路 OV7670 视频系统。  
> 目标：通过时钟域拆分、控制路径解耦和 SLR 局部化，减少当前时序违例并完成真实时序收敛。  
> 文档状态：待在实际仓库中核验和实施的设计规格，不是已经验证的 RTL。本文未打开实际 RTL、MIG 配置或 routed DCP，也未执行仿真、综合、布线或板级验证。

## 0. 给 Codex 的直接执行指令

请在当前实际工程仓库中，依据本任务书实施视频系统的架构级时序优化，不要只给分析建议。

先完成 P0 基线核验和代码定位，再按 P1～P6 分阶段修改、测试并记录结果。每个阶段必须有可复现构建方式、功能验证和与基线可比的证据；适用时完成 routed timing 对比。不能用一次大规模重写替代阶段验收，也不能只修摄像头入口而跳过违例最多的 DDR frame reader。

本任务的目标架构为：

**局部 300.120 MHz 采样恢复区 → 小型事件 CDC → 150.060 MHz 视频处理主干 → 队列化 DDR 接口边界 → 局部 300.120 MHz MIG 接口区。**

跨 SLR 的数据、VALID、反压和必要控制都必须通过有容量保证的寄存边界。宽 payload 不再普遍参与全局 reset/run 控制；采集启停与硬件复位分开；发生溢出时不得把残帧发布成完整帧。

### 0.1 不可违反的边界

1. **当前实际基线为 8 路，不是 16 路。** 预留 16 路参数化和分组扩展接口，但本轮先保证现有 8 路。不得用减少通道数、关闭显示或停用预处理来伪造达标结果。[R1 §1、§9]
2. **保持当前非 Gemmini 基础视频系统的范围。** 不新增 Gemmini，不顺带更改 Rocket/RVV/软件调度架构；已有基础 SoC 功能继续保留。[R1 §9]
3. **保留现有异步过采样原理。** 不把 `cam_pclk` 或 `pixel_ce` 改接为 fabric clock，不在本轮同时重写 PCLK 恢复算法和调整其时间参数。[R1 §3]
4. 不随意更改传感器初始化、SCCB、XCLK、板级引脚、电气属性、DDR 器件时序或 HDMI 专用时钟。150 MHz 目标仅针对拟迁移的视频处理逻辑。
5. 第一版保持现有 RGB 转换规则、帧内存布局、地址空间和软件可见寄存器语义；未知接口先核查，不能假定 MIG 是 AXI、固定某个位宽或固定某个 SLR。
6. 不用扩大 `false_path`、放宽真实时钟周期、无依据的 `multicycle_path` 或豁免内部控制路径来消除违例。新架构必须在真实目标时钟下分析。
7. 不覆盖、删除或重建不必要的现有工程数据。先记录用户未提交修改；不要执行 `git reset --hard`、`git clean -fdx` 或无范围的目录删除。修改厂商生成文件前应优先找其可复现配置来源。
8. 没有真实仿真/布线/板测结果时，明确写“未执行”或“阻塞”，禁止生成看似成功的虚构报告。默认不自动下载比特流、不复位实验板，也不结束其他用户进程。

### 0.2 事实、推断与设计要求的区分

- **[R1] 基线事实**：来自用户提供的《PCLK 架构与当前时序违例分析》，全文原样附在本文末尾。
- **待验证推断**：例如 writer 容量状态经 READY 链影响 camera FIFO RAM 控制，必须检查综合网表，不能仅凭层级名称认定 RTL 的直接依赖。
- **本文设计要求**：150 MHz 视频域、事件桥、队列接口、分阶段任务等，是拟实施方案，不代表这些模块已经存在。
- 本文建议的新模块名、文件路径和信号名均为工作命名；已有等价实现优先复用。原报告中的行号只用于定位，不作为匹配代码的硬条件。

### 3.2 时钟职责

| 时钟域 | 保留的功能 | 不应继续集中在该域的功能 |
|---|---|---|
| capture，约 300 MHz | 输入采样、亚稳态捕获、现有 PCLK 恢复、依赖采样周期的过滤、必要的轻量故障状态 | 大缓存读控制、DDR 状态、逐像素 DDR 打包、全局宽统计 |
| video，约 150 MHz | RGB 拼接、像素/行帧状态、本地缓存、分组传输、帧管理、读写请求生成及数据整理 | 未同步的原始 DVP 输入、必须由 MIG UI 时钟驱动的接口状态 |
| DDR UI，约 300 MHz | MIG 边界握手、局部容量记账、必要发射/接收缓冲 | 完整像素算法、全局帧状态广播、逐通道大量诊断 |
| 既有 HDMI/控制域 | 原来确实需要该时钟的显示、PHY、SCCB 等 | 不因重构统一改接为 video_clk |

“局部采样区”主要表示功能和布局局部化，不默认增加八个独立采样时钟。

### 3.3 时钟生成与 CDC 选择

- 优先研究从既有 UI 时钟经适用的**专用时钟资源**获得实际 2:1 关系的 video 时钟；是否使用分频 BUFG、Clocking Wizard 或其他资源，由器件和当前工程核验后决定。
- 禁止普通逻辑翻转寄存器输出直接作为全局时钟；禁止把“每两拍 CE”称为已经实现的 150 MHz 时钟域。
- 150.060 MHz 是原报告频率的一半目标值。最终频率和约束以实际时钟资源及工具报告为准；不照抄 `mmcm_clkout0` 这类可能变化的自动名称。
- 采用双时钟 FIFO，不等于可以将两整片时钟域全部设为异步豁免。真实时钟关系照实建模，CDC 约束作用于核验过的跨域结构。
- 采用同步比例转换时，先证明来源、频率比、相位关系和复位/启动条件满足所选实现要求。不能只因为标称“300/150”就认定满足。
- 不在同一个阶段同时更换 PCLK 算法、提高/降低采样时钟和改变 DDR 参数。保持因果可追踪。

### 3.4 分阶段迁移期间也必须保持合法时钟边界

不能只保证最终架构正确，而让中间阶段出现同步 FIFO 两端异钟或直接跨域握手。

| 构建阶段 | 前端/像素处理 | DDR 高层处理 | 必须存在的真实边界 |
|---|---|---|---|
| P1/P2 | 保持当前 300 MHz | 保持当前 300 MHz | 同钟 FIFO 与寄存切片，不新增无依据 CDC |
| P3 | capture 300 MHz，像素/本地缓存 150 MHz | 尚未迁移的部分仍为 300 MHz | capture→video 事件 CDC；video→旧 DDR 链也必须有真实转换 |
| P4 之后 | capture 300 MHz，像素/视频主干 150 MHz | 高层 150 MHz，UI 适配器 300 MHz | 事件 CDC 和稳定的队列化 video↔UI 边界 |

尤其不能把 P2 已改成同步的 FIFO，在 P3 中悄悄变成写侧 150 MHz、读侧 300 MHz。若 P3 暂时保留旧 writer/reader，必须补正确的过渡桥，并在 P4 完成后清理冗余转换；或将相关迁移作为一个不可分割的、完整验证的构建切换，同时保留阶段级测试证据。

HDMI RX/TX 和其他客户端同样按实际时钟核对，不允许因端口仍叫 `video_clk` 就默认同域。

### 3.5 SLR 拓扑

原报告的布局意图是 CH1～CH4 从 SLR3 经 SLR2 到 SLR1，CH5～CH8 从 SLR2 到 SLR1，恢复集中在 SLR1。[R1 §3.3]

新方案优先让每路的采样、同步、恢复、事件桥和前端缓冲靠近其 IO 所在区域，再通过寄存化接口向实际 DDR 区输送恢复后的数据。按相邻四路分组是首选候选方案，不是未经资源分析的硬性布局结论。

允许一条数据流经过多个 SLR，但不允许同一短周期控制链反复跨区往返。同步级不能为了满足分组美观被拉到远处；跨区流水应放在可靠同步/恢复之后。

### 4.1 恢复事件接口：不能只在有像素时发数据

**必须保留空白时段的 HREF/VSYNC 边界事件。** 否则 CDC 两侧即使像素值正确，也可能丢失帧开始、行结束或停机边界。

建议逻辑记录包含：

```text
sample_valid          本记录是否包含一个恢复后的输入字节
sample_data[7:0]      该字节
对齐后的 href/vsync  与该字节属于同一逻辑采样时刻的控制状态
控制变化标志         即便 sample_valid=0，也可表达行帧边界
fault 标志           失锁、无法表示的输入异常等
stream_epoch         重同步代次；确有需要时引入
```

这只是语义字段，不规定最终位宽、打包布局或 RTL typedef。

必须满足：

- 数据和 sideband 作为同一有序记录跨域，不分别同步后再猜测对齐关系。
- 同拍出现字节与控制变化时，按原 RTL 的事件顺序处理；不能为了方便把“新 HREF”错误地配给“旧字节”。若一条记录不能无歧义表示，就使用组合事件字段或有容量保证的序列化机制。
- 将采样周期过滤留在高速侧。只有证明与采样时间无关的字节/像素/行帧处理才能迁入 video 域。
- 若使用每拍最多一次 FIFO 写入，必须证明事件合并不会漏事件。事件率预算包括边界和故障，而不只包括 nominal PCLK 数据字节。
- 噪声或异常输入可能破坏正常事件率假设。此时走显式 overflow/abort/resync，不能无声丢弃边界。
- 协议改变增加延迟是允许的；正常输入下的像素值、有效像素顺序、行帧边界必须与旧版等价。

### 4.2 FIFO 满时，故障通知不能依赖同一个已满 FIFO

摄像头不能被 READY 停住，因此每个不能反压的入口必须定义溢出策略。

推荐策略：记录本通道当前帧失败，停止接纳该帧后续内容；通过不会被数据 FIFO 满阻塞的可靠状态握手传递故障；待旧数据隔离/排空和故障被确认后，在完整新帧边界恢复。

可采用粘滞故障位配 request/ack、稳定的故障描述符握手或已有等价结构。要求：

1. 请求未应答时信息保持稳定，不因第二次事件覆盖第一次的关联帧/代次。
2. 不能直接跨域传一拍脉冲，也不能假设 toggle 能承载任意事件速率。
3. 错误通知必须关联被影响的通道和帧/代次；旧故障不能误杀后来正常帧。
4. 正常帧提交不能抢在可靠的完成/错误判定之前。不得假设另一条 CDC 路径上的 fault 一定比 EOF 更早到达。
5. 代次计数回绕不能与仍在途的旧数据混淆。位宽和回收边界必须有依据。

优先复用既有可靠的残帧隔离协议；不足时补最小 `FRAME_CLOSE/FRAME_ABORT` 或等价握手，不要求为了字段名称重写全部框架。

### 4.3 同步本地缓存与真实 CDC 分开

P2 在当前同钟结构内，可把 `camera_axis_cdc` 的 XPM async FIFO 替换为同步实现；P3 新增真正的 capture→video 事件桥。两者职责不同。

不得假定同步 FIFO 没有 `rst_busy` 或不需要复位协议。Codex 必须核查实际 Vivado 2023.2 XPM 配置的端口、复位要求、读模式、`data_valid`/`empty` 语义和输出延迟。

第一版保持**等效像素容量**及原有溢出策略。改变位宽时不能仅保持相同 DEPTH 数字而意外缩小容量。深度缩减属于后续独立优化。

### 4.4 RAM 读控制必须本地化

FIFO 出口应采用：

```text
本地 RAM/FIFO → 本地预取控制 → 输出暂存队列 → 全寄存弹性接口
```

发起一次 RAM 读取时，为返回数据预留一个本地输出槽位。不能把读请求发出和数据实际返回当成同一拍，除非当前实现确实如此且已验证。

基本不变量：

```text
output_used + pending_read_returns <= output_capacity
```

新增读请求必须基于本拍出队、已返回和新增请求的正确 next-state 容量计算。远端 `m_ready` 不得通过组合路径直接参与 RAM `rd_en/REGCE/EN`；它只影响本地弹性队列的下一状态。

必须覆盖 simultaneous push/pop、读延迟、满/空边界、长停顿后恢复以及 FIFO 复位恢复。不能仅在持续 `ready=1` 时验证。

### 4.5 跨 SLR 弹性接口必须真正切断反压

接口要求：

- payload、VALID、SOF/EOL、通道标识及其他必需 sideband 在正向边界一并寄存。
- READY 或等价容量信息反向寄存，不能只寄存 DATA。
- 缓冲容量覆盖反压传播期间仍会到达的数据，以及已经预留但未返回的数据。每个在途项只计一次，不能遗漏也不能重复记账。
- 接收握手定义为 `valid && ready`。输出阻塞时 payload 和 sideband 保持稳定。
- 经过初始化后，在上下游持续可传输时支持每拍一个 beat，不允许固定插入空拍。
- 有时钟跨越时使用真实 CDC 结构，不能把普通寄存切片当 CDC。

禁止如下“优化”：只写 `ready_q <= downstream_ready`，却不增加/核查在途数据的存储能力。

建议使用仓库内已验证的全寄存弹性切片，或经版本核验的厂商 IP。新写模块时必须单独完成随机背压测试。

## 5. DDR 与帧事务边界

### 5.1 Writer 与 reader 同时纳入重构

Reader 是原报告中失败端点最多、TNS 绝对值最大的类别，不能把它留为未分析的大块 300 MHz 逻辑。[R1 §5.2]

将读写结构统一为：

```text
video 域：请求生成 + 数据组织 + 客户端状态
    ↓ / ↑
明确容量和事务关联的请求/数据/返回队列
    ↓ / ↑
UI 域：必要的 MIG 协议发射/接收 + 小范围容量记账
```

不要求原有每个状态机都强行迁移。直接依赖 UI 握手的必要状态留在 UI 域，其余状态通过队列解耦。分界依据是协议依赖，而不是文件名。

### 5.2 请求、数据和返回不得错配

Codex 应定义并记录写/读描述符的最小语义，例如：

```text
写请求：客户/通道、目标地址、长度、字节有效信息、帧/代次标识
写数据：与该请求对应的有序数据、必要的尾拍有效信息
读请求：客户、源地址、长度、返回目标/标签
读返回：能恢复原客户和请求顺序的数据、完成/错误状态
```

实际字段和是否使用 ID 必须与当前协议相适配。不强制引入多 outstanding、多 ID 或乱序能力。

- 独立命令队列和数据队列必须有明确配对规则，不能因其中一个 FIFO 先被接收而错配后续请求。
- 输出 stalled 时，地址、长度、mask、ID 等相关字段保持稳定。
- 同一帧的写完成和 READY 发布必须有确定的顺序关系。
- 复位、abort 或清队列不能把新请求的数据与旧请求绑定。

### 5.3 MIG 是 AXI 时

先确认实际 AXI 版本、位宽、burst 约束、ID/ordering、outstanding 支持和原适配器行为，再决定复用或引入时钟/位宽转换。

需要验证 AW/W/B 与 AR/R 各自背压，以及写响应与帧提交的关系。不能把 AW 握手、W 最后一拍握手、B 响应三者混为一谈；应采用当前系统对帧可读性的真实要求定义完成。

不得把 DDR 服务端压力通过未经寄存的多级 READY 链传播回摄像头 RAM。

### 5.4 MIG 是 native 时

必须以实际 native 端口协议定义命令接受、写数据接受、返回时机、mask 和可否背压。

若读返回不能被暂停，则**在发出读命令之前**预留所有返回数据的缓冲容量：

```text
return_fifo_used + reserved_not_yet_returned <= return_fifo_capacity
```

发出新命令时新增预约，返回入 FIFO 时把预约转成占用，消费返回数据时释放占用。按实际返回 beat 数、位宽和突发长度计数，不能按“请求个数”替代字节/beat 容量。

若 native 没有独立写完成响应，不得凭空创造“DDR 已落盘”的确认。应记录实际接口能够保证的接受与顺序关系，并据此设计读后写可见性和帧发布屏障；无法证明时属于阻塞，不得假定完成。

### 5.5 帧发布和安全回收

复用现有帧管理框架，并至少满足下列逻辑所有权关系：

```text
FREE → WRITING → READY → READING → FREE
          │
          └→ ABORT_PENDING / DRAINING → FREE
```

状态名称不要求与此一致，但行为必须一致：

- 仅在本帧输入完整、预期行/像素满足、没有 ingress/FIFO 错误、帧关闭有效且 DDR 写入达到定义的安全边界后，才可发布 READY。
- 仅数够最后一个像素、看见最后一个 EOL 或发出最后一个写请求，不自动等于完成。
- 若使用独立故障通知 CDC，需要保证其与 frame-close 的排序；更简单的实现可以仅为无故障帧产生可靠成功关闭，错误帧不得产生可发布完成。
- abort 后，已经被接受的 DDR 事务仍可能完成。该 buffer 不能立即分配给下一帧，否则旧数据可能覆盖新帧。
- 等待旧事务达到安全排空边界后才能回收；显示/预处理正在读取的 buffer 也不得被写者抢占。
- 异常恢复以完整新帧边界为准，不从任意字节或半个 RGB565 像素重新开始。
- 明确失锁、摄像头停钟、overflow、capture disable、DDR 不可用和各域复位时的行为。

这些要求不意味着必须新增复杂多 producer 或原子 reservation 系统；本任务只需要现有视频客户端的正确容量与所有权记账。

## 6. 复位、运行控制和诊断

### 6.1 优先修复 enable 与异步 reset 混用

原报告定位的高风险形式为：

```text
capture_resetn = video_resetn && capture_enable_sync2
```

其后形成 LUT 驱动异步 CLR，涉及八路相关 `LUTAR-1`。[R1 §6.2]

重构要求：

| 信号类别 | 语义 | 使用限制 |
|---|---|---|
| hardware reset | 让必要控制状态进入已知状态 | 按实际时钟域/IP 要求同步释放；不混入普通 enable |
| capture enable | 请求开始/停止正常接收 | 进入同步 FSM/握手，不直接驱动异步 CLR |
| abort / flush | 当前事务无效或要求排空 | 显式协议处理，不默认等于全域 reset |
| clock ready / calibration ready | 时钟和 DDR 已可使用 | 同步到各消费域，参与本地启动流程，不无界广播 |

若安全需求要求立即禁止发布，可先同步设置本地禁止状态，同时走 abort/drain；不得用组合 reset 代替完整事务处理。

### 6.2 启停和复位顺序

建议行为：

```text
启动：
时钟稳定 → 必要 reset 完成 → FIFO 两侧 ready/busy 条件满足
→ 下游具备接收能力 → 等待完整帧边界 → 正常采集

正常停止：
停止接收新帧 → 完成或明确作废当前帧
→ 排空/隔离已接收数据与 DDR 事务 → 停止

异常：
标记受影响帧无效 → 阻止发布 → 隔离旧数据
→ 完成安全清理/必要 FIFO 复位 → 等待新完整帧
```

FIFO 某一侧单独复位不应被默认为安全。必须查明所用 FIFO 对两侧 reset 的要求；系统支持独立域复位时，应有协调握手和失效处理。

### 6.3 payload 少复位，控制状态明确初始化

优先检查并移除不必要的宽 payload reset，例如像素数据、打包数据、仅由 valid 保护的流水数据和 RAM 内容。

必须保留或以明确初始化流程替代的状态包括：有效位、FIFO 指针、占用/预约量、帧所有权、事务标签、必要 FSM 状态及安全启动状态。

不能盲目删除计数器 reset：一个计数器若决定地址、行边界或容量，不属于可随意忽略的诊断数据。

不复位 payload 后，必须证明它在第一次有效使用前已经写入。输出阻塞时仍要遵守稳定性协议，不能为减少 CE 让 payload 自由变化。

### 6.4 局部分发而非继续扩大同步器扇出

同步器后增加普通寄存分发级，按区域形成少量本地 reset/run 状态；不要复制多份独立 CDC 同步器后假定释放必然同拍。

不同区域存在一拍或数拍启动差异是可接受的前提，是接口通过 ready/valid 或显式 ready 握手保护。依赖全系统同拍释放的结构需要先改协议，不能简单复制寄存器。

检查去 reset 后是否把同一高扇出 reset 原封不动换成高扇出 `run/valid`。改造目标是局部控制，不是信号改名。

不全局滥用 `DONT_TOUCH`、`KEEP`、`MAX_FANOUT`；是否使用和位置必须有实际网表/物理证据。

### 6.5 诊断迁移

- 区分参与 PCLK 恢复决策的状态与纯观察统计，前者不因“看起来像计数器”就迁走。
- 高速域仅保留必要事件采集与容量适当的局部统计，长周期汇总/软件快照下沉。
- 一拍脉冲不能直接跨到低频域。精确事件计数采用有速率和回绕保证的计数/快照机制；关键故障用可靠握手。
- 使用 Gray 计数方案时，核验单次更新形式、采样约束和回绕预算；不能把任意多步递增的二进制计数简单转 Gray 就视为可靠。
- 快照数据在传输期间保持稳定，ack 前不覆盖；诊断通道堵塞不得反压主视频流。
- 首轮保持必要软件可见统计语义。确需减少精度或采样率，单列变更，不作为隐式优化。

## 7. 吞吐、缓存与调度预算

### 7.1 先核算实际需求，不直接固定主干位宽

原报告给出 nominal PCLK = 24 MHz，RGB565 两字节组成一像素，再展开 RGB888。[R1 §3.2、§3.4]

以下只是按报告参数的上界示例，不代替测量和实际格式核查：

```text
有效字节最大输入率：24 MHz × 1 B = 24 MB/s/路
像素最大输入率：24 / 2 = 12 Mpixel/s/路
RGB888 载荷：12 × 3 = 36 MB/s/路
四路载荷：144 MB/s
八路载荷：288 MB/s
十六路载荷：576 MB/s
```

不计消隐、协议开销和其他客户端；十六路仅是扩展预算示例，不代表当前已实例化十六路。

在 150.060 MHz 下：

| 总线位宽 | 理论载荷能力，未扣除开销 |
|---|---:|
| 64 bit | 1.20048 GB/s |
| 128 bit | 2.40096 GB/s |
| 256 bit | 4.80192 GB/s |

实际总线需要计入 beat 利用率、字节有效、请求空拍、仲裁、CDC、读写切换和现有 HDMI/预处理/其他 DDR 客户端。不能直接用摄像头写入量代表整个 DDR 流量。

若目标是保留某条既有 300 MHz 总线的全部峰值能力，降到一半频率后需要用位宽或并行能力补足；但视频主干也不必无条件等于 MIG 的全部峰值，只需满足明确的系统吞吐和服务保证。

### 7.2 保留等效缓存容量后再缩减

原结构每项两像素、48 bit payload、深度 16,384：[R1 §3.4]

```text
单路 payload 容量 = 16384 × 48 / 8 = 98,304 B = 96 KiB
八路 payload 合计 = 768 KiB
```

不包含 sideband 和物理资源开销。

缓存预算采用：

```text
所需容量 ≥ 输入峰值率 × 最大服务空窗
           + 未计入的额外突发/在途数据
           + 安全余量
```

例如 36 MB/s 的 RGB888 输入在 100 μs 无服务时产生约 3.6 KB 数据；该数值仅示范计算方法。实际最大服务空窗必须由调度上界、测量或两者给出，不能直接照用 100 μs。

任何 FIFO 缩深度都单独提交，并说明减少的是哪一段缓存、单位如何换算、最长服务空窗是否仍被覆盖。

### 7.3 分组调度

推荐按邻近 IO 分组，初始候选为每组四路。每路有独立输入缓存，组内使用有最大等待界限的轮询/配额调度，按有限块或现有 burst 粒度提交。

- 不以整帧作为唯一不可抢占单位而造成其他摄像头无界等待。
- 不新建一个跨所有 SLR 的逐像素全局组合仲裁器。
- 描述符、数据和通道归属必须保持关联。采用头部标签或逐 beat 标签均可，但必须覆盖背压下的切换。
- 显示读出若有硬实时需求，应有可说明的带宽/延迟保证；不能给予其他客户端无限期严格优先级。
- 平均 DDR 吞吐长期小于总输入时，增加有限 FIFO 不会解决持续积压。必须进入可见的丢帧策略或修复服务预算。

### 7.4 可选后续优化，不属于首轮功能等价改造

可评估在采集缓存和 DDR 中保留 RGB565，到显示/推理边界才展开 RGB888。同像素数下 payload 从 24 bit 降到 16 bit，减少三分之一。

这会改变缓存/DDR 格式和消费者接口，首轮禁止默认实施。只有时钟/控制重构稳定后，单独提供格式兼容性方案和逐像素验证，再决定是否引入。

## 8. XDC、CDC 与物理实现要求

### 8.1 修复例外重叠，但不把约束清理当成时序优化成果

原报告指出 IOB→第二级 sync 的 1.5 ns max-delay 和 false path 同时命中 88 个端点。[R1 §4.2]

Codex 必须列出并分别核查：

```text
外部异步 pad → 第一级 IOB 捕获
第一级 IOB → 后续同一采样时钟捕获级
可靠同步/对齐后 → 恢复逻辑
```

不得因为第一级可能亚稳就扩大豁免到整个内部同步链。对 `set_max_delay -datapath_only` 的 hold 处理及例外优先级，必须查本机 Vivado 2023.2 的说明并用实际 max/min 点对点报告验证；不能只删 false path 就宣布两类检查完整。

保留真实必要的异步接口处理，同时限制捕获级间物理距离并检查有效覆盖。同步级属性、布局与 CDC 报告应相互一致。

### 8.2 新增时钟域的覆盖

- 通过实际时钟源/输出 pin 查询对象，避免依赖脆弱的自动生成时钟名。
- 新增 clock、reset、status、frame-control、diagnostic crossing 都纳入 CDC 清单，不能只检查数据 FIFO。
- 每个 CDC 结构记录时钟来源、同步方法、约束来源和报告定位。
- 不把多比特 payload 逐位同步，不用无依据的宽总线 false path 替代传输协议。
- 新增例外逐条注明对象、原因、命中数量和验证方法；命中为零或异常变大时构建应提示失败或明确告警。
- 22 个无 input delay、57 个无 output delay 等旧缺口按实际接口分类处理，不能机械补零延迟。[R1 §6.1]

### 8.3 物理局部化

1. 在完成接口寄存化后，查看每路/每组资源与实际 IO、MIG 区域位置，再确定 Pblock。
2. 将紧密耦合的恢复、事件 FIFO、本地缓存及其控制尽量放在邻近区域；避免只约束少数 sync 寄存器而剩余模块自由跨区。[R1 §3.3]
3. 跨 SLR 链路在边界预留流水/缓冲；检查反向 READY 和 reset/run 路径同样是否跨区。
4. 不未经资源分析就强制完整前端和大 FIFO 塞入狭小区域。先采用有余量的区域引导，再以实际布线修正。
5. 可评估适用的 SLR crossing register/Laguna 资源，但不对所有寄存器统一施加特殊放置属性。
6. RAM/FIFO 的读控制与输出缓存优先相邻；设计层级局部化后，还要确认综合优化没有重新形成跨模块长控制锥。

### 8.4 独立跟踪 MIG/IP 和外部 DVP 风险

外部异步过采样的可靠性不能仅由“没有 `cam_pclk_*` 负 slack”证明，仍需边沿相位、稳定窗口、抖动与失锁恢复测试。[R1 §3.2、§4.1]

MIG/IP 的现有失败端点不得直接豁免。区分 IP 内部、外围接口以及布局拥塞原因；必要时按真实工具/IP 配置调查，不手改受保护 PHY 或放宽 DDR 时序。

### 10.1 建议必须实现的断言/scoreboard 不变量

```text
I01：valid && !ready 时，valid 与 payload/sideband 保持稳定。
I02：写入数 - 读出数 = 当前占用；占用不超界。
I03：已占用输出槽 + 已预约未返回 RAM 读 <= 输出容量。
I04：读返回 FIFO 占用 + 未返回 DDR 预约量 <= 返回容量。
I05：每个成功输入记录恰好产生一次有序输出，除非显式 abort 丢弃。
I06：所有丢弃都可归因于明确 fault/abort，不存在静默数据损失。
I07：发布 READY 的帧满足完整性和定义的 DDR 安全完成条件。
I08：WRITING/READING/READY 等所有权不冲突。
I09：abort 后旧事务未安全排空前，其 buffer 不可重新分配。
I10：跨域 request 未 ack 时，对应多比特状态不被修改。
I11：新帧/新代次不消费旧代次残留数据。
I12：FIFO reset/busy 阶段不产生非法读写握手。
```

复位或协商完成的链路 flush 可以定义为协议重启边界；不能把普通 abort 加进 assertion disable 条件以掩盖 stalled 数据被修改的问题。

## 12. 最终验收与不达标处理

### 12.1 架构验收

- 恢复后的像素/帧处理和 reader/writer 高层控制已经与 300 MHz 采样/UI 接口分离。
- 未迁出的 300 MHz 自定义模块有明确的接口/时间语义理由，不是遗漏。
- 远端逐拍 READY、reset/run 不再直接组合控制跨区 RAM enable。
- 所有跨域数据、故障、帧控制、复位状态和诊断传递都有定义和验证。
- 溢出、失锁、停启、延迟写入都不会发布残帧或提前复用 buffer。

### 12.2 时序与方法学验收

完整目标配置、真实目标时钟和完整有效约束下：

```text
WNS >= 0
TNS = 0
setup 失败端点 = 0
WHS >= 0
THS = 0
WPWS >= 0
TPWS = 0
```

同时，相关八路 `LUTAR-1` 已修复；新引入或关键 CDC/约束问题已解决；剩余工具告警逐项记录实际影响和理由，不盲目要求所有无关 advisory 为零，也不静默忽略真实问题。

可争取额外 setup 裕量作为工程目标，但本文不承诺改完必然得到某个正 WNS。原报告的 +0.003 ns hold 裕量虽非负，仍应在所有改动后重新检查，不当作可消耗的“无风险余量”。

### 12.3 功能与性能验收

- 原有 8 路及当前所有既有客户端功能保留，RGB/帧协议和软件可见语义兼容。
- 第 10 节适用场景通过，端到端数据可由 scoreboard 或板级可复现方法核对。
- 吞吐目标及测试条件在 P0 明确；不能靠降帧率、减少分辨率或关闭客户端达成时序目标。
- 缓存、最大服务空窗、读写带宽与丢帧策略有测量或可说明的预算依据。
- 没有板测条件时，标记“完成 RTL/仿真/实现验证，板测未执行”，不得宣称已具备生产稳定性。

### 12.4 未收敛时的处理

保留真实失败结果，按新分类继续定位最严重控制网、剩余 reader/UI 路径、跨 SLR 往返和拥塞。每次追加改动仍应单因素可追踪。

禁止将尚未解决的 MIG/IP 路径、外部 DVP 风险或新增 CDC 风险归为“与任务无关”。可以分开处理，但必须留在最终问题清单。

### 3.3 SLR 管线意图

`xdc/clk.xdc:135-162` 使用 soft pblock 引导：

- CH1～CH4：IOB(SLR3) -> sync(SLR3) -> pipe(SLR2) -> recovery(SLR1)。
- CH5～CH8：IOB(SLR2) -> sync(SLR2) -> pipe(SLR1) -> recovery(SLR1)。

这些约束只引导 `sync` 和 `pipe` 寄存器，且 `IS_SOFT=true`，不会硬性固定完整前端、FIFO、DDR writer/reader 的位置。

### 3.4 `camera_axis_cdc` 的当前角色

在 `rtl/video/camera/camera_subsystem.sv:138-159` 中，`camera_axis_cdc.camera_clk` 与 `ddr_clk` 都连接 `capture_clk`。因此当前实例中的 XPM async FIFO并不承担真实的异步时钟跨越，而主要承担：

- RGB888 两像素拼成 48 bit；
- SOF/EOL 携带；
- 深度 16,384 的弹性缓存；
- 前端无法停顿时的溢出隔离与诊断。

## 4. PCLK 相关约束现状

### 4.1 外部 DVP 约束

有效物理 XDC 在 `xdc/vu13p_ov7670_8ch_fmc1_fmc2_j2_cam3_legacy_v3.xdc:215-254` 中完成：

- DVP 输入设置 `IBUF_LOW_PWR=FALSE`；
- 对 8 路 PCLK 分别创建 24 MHz 时钟 `cam_pclk_1..8`；

不过功能采样寄存器的真实时钟是 300 MHz，而不是这些 24 MHz PCLK。`xdc/clk.xdc:84-92` 又将 pad 到第一级 IOB 的 DVP 路径全部设为 false path，所以实现报告把 `cam_pclk_1..8 -> mmcm_clkout0` 列入 User Ignored Paths。结论是：

- 24 MHz `create_clock/set_input_delay` 描述了外部接口时序意图；
- 它没有对当前“300 MHz 异步过采样”的 pad-to-IOB 捕获给出常规 setup/hold sign-off；
- 当前报告里不存在 `cam_pclk_*` 域的负裕量，也不能据此断言外部 DVP 接口已经由 STA 完整验证。

### 4.2 1.5 ns 约束重叠风险

`xdc/clk.xdc:98-108` 对 IOB 到第二级 sync 设置了 1.5 ns datapath-only max delay，但 `xdc/clk.xdc:114-133` 又对相同 sync 端点设置 false path，并显式覆盖 IOB 的 C/Q launch pin。

本次 `report_exceptions -coverage` 显示：

- 1.5 ns max-delay 命中 88/88 个端点；
- 后续 false-path 同样命中这些 88 个端点。

这属于重叠例外。由于 false path 的优先级高于普通 max delay，1.5 ns 物理预算很可能不会作为最终 sign-off 检查发挥预期作用。后续应把“亚稳态捕获路径不做同步 setup 检查”和“限制 IOB 到 sync 的物理距离”拆成不互相覆盖的实现约束，并用点对点 `report_timing`/`report_exceptions -ignored` 验证。

## 7. 根因判断

按证据强弱排序：

1. **300 MHz 域负载过大且控制集过宽。** 该时钟驱动约 123,972 fanout；全部负裕量都在此域，且约 84% endpoint 是 enable/reset 类 pin。
2. **跨 SLR 布线主导。** 最差路径只有 3 级 LUT，但 route 占 94%，并发生 SLR1/SLR2 往返。
3. **相同时钟两侧仍使用大深度 async FIFO。** 8 个深度 16K 的 `camera_axis_cdc` 带来 XPM RAM 控制和 reset-busy 网络，最差路径直接落到其 RAM enable。
4. **复位被用作大量 300 MHz 数据/控制寄存器的同步控制条件。** per-channel reset 已本地同步，但继续扇出到前端、stream、FIFO 和诊断，形成大面积 CE/R 路径。
5. **诊断逻辑规模加重拥塞。** PCLK recovery 有大量 32/64 bit 计数器和快照状态；它不一定制造 WNS，但扩大了 300 MHz 域的寄存器、reset 和 enable 负载。
6. **PCLK 约束模型没有完整 sign-off 异步过采样接口。** 这不是当前 20,800 个负裕量的来源，但属于独立可靠性风险。

## 8. 建议的优化顺序

1. 先处理 `camera_axis_cdc`：当前同钟情况下改用 synchronous FIFO，或至少使用相同时钟模式下更简单的 BRAM FIFO/寄存切片，消除不必要的 pointer CDC、reset-busy 和复杂 RAM enable。
2. 从 300 MHz payload/计数器寄存器中移除大范围同步 reset；用局部 `valid/run` 状态屏蔽无效数据，只复位真正需要确定上电状态的控制寄存器。
3. 修复 8 路 `LUTAR-1`：不要让组合出来的 reset 条件直接驱动异步 CLR。采用异步置位/同步释放的单一原始 reset，功能 enable 只进入同步状态机或 CE。
4. 对 reset、run、FIFO enable、诊断 clear 等高扇出信号做分层本地复制，并在消费者附近增加寄存边界；逐类比较 TNS，而不是只盯 WNS。
5. 对 writer、camera FIFO 和 stream 做 SLR 物理分区，避免同一控制锥 `SLR1 -> SLR2 -> SLR1` 往返；当前 soft PCLK pblock 不足以约束完整 300 MHz 数据流。
6. 把非实时诊断统计移到较低频域，或在 300 MHz 域只保留窄事件脉冲/Gray counter，再跨域汇总。
7. 清理 DVP 例外重叠，明确 1.5 ns 物理预算是否有效；补跑 `report_cdc`，定位 `TIMING-10`。
8. 每次修改后从 routed checkpoint 导出全部负路径并按本文章节 5.2 同样分类。收敛标准应为：`WNS >= 0`、`TNS = 0`、`WHS >= 0`、`THS = 0`，同时清除 PCLK 相关 `LUTAR-1` 和关键约束覆盖缺口。

## 9. 当前状态判定

当前 bitstream 可以生成，也可能在实验室条件下正常工作，但这不等于完成时序签核。以当前报告为准，300.120 MHz 域仍有 20,800 个 setup 失败端点，在工艺、电压、温度变化下不能保证稳定。

下一阶段应先保持当前非 Gemmini SoC 不变，优先缩小 300 MHz 控制集与跨 SLR 拥塞；PCLK 外部接口约束和异步复位毛刺问题并行清理。只有基础视频系统达到零负裕量后，再重新加入 Gemmini，才能区分基础架构问题与新增计算资源带来的拥塞。
