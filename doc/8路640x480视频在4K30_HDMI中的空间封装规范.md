# 8 路 640x480 视频在 4K30 HDMI 中的空间封装规范

## 1. 目的与范围

本文规定 8 路 640x480@30 FPS 视频如何封装到一路 3840x2160@30 FPS
HDMI RGB 视频中，以及接收端如何在进入 DDR 前恢复为 8 路独立视频流。

本文作为后续 HDMI 汇聚发送端、HDMI 空间拆分接收端、仿真模型和验收测试
的共同依据。本文只规定视频数据面，不规定 HDMI PHY、EDID、DDC、时钟芯片
寄存器和 AI Runtime。

## 2. 固定方案

采用整帧空间封装：

    8 路 640x480
        -> 4 列 x 2 行的 8 个 960x1080 槽位
        -> 每个槽位中央放置一幅原尺寸 640x480 图像
        -> 槽位剩余区域填充黑色
        -> 输出 3840x2160p30 RGB

不对摄像头图像做缩放，不改变图像宽高比，不把 8 路图像写成一张 DDR
中的 4K 帧后再拆分。发送端直接从 8 路最新完整帧生成 HDMI transport，
接收端在 AXI4-Stream 域完成空间裁剪。

选择 4x2 槽位的原因：

- 3840 / 4 = 960，2160 / 2 = 1080，槽位边界简单且固定；
- 每个槽位的图像位置完全相同，RTL 可复用同一套裁剪逻辑；
- 图像起止坐标均为偶数，适配 HDMI RX 的 2 pixels/clock；
- 8 路布局规则、对称，便于产生测试图和人工检查；
- 黑边由发送端实时生成，不增加 4K DDR 帧缓存。

## 3. HDMI Transport 参数

第一版必须固定为：

| 项目 | 要求 |
|---|---|
| 有效分辨率 | 3840x2160 |
| 扫描方式 | progressive |
| 帧率 | 30 FPS |
| 输入颜色 | RGB |
| 颜色深度 | 8 bit/component |
| AXI 视频数据 | 48 bit，2 pixels/clock |
| 单像素格式 | RGB888；XRGB 的 X 不通过 HDMI 传输 |
| 4K 帧像素时钟 | 297 MHz HDMI pixel rate，由 HDMI IP/VPHY 负责 |
| AXI 视频时钟 | 通常为 148.5 MHz，取决于 HDMI IP 的 2 PPC 配置 |

接收端必须拒绝或标记以下输入：非 3840x2160、隔行、非 RGB、非 8 bit、
非 2 PPC 或非 30 Hz。不能静默地把其他模式当作本规范输入。

## 4. 坐标和槽位定义

4K transport 的像素坐标为 x=0..3839、y=0..2159。

槽位尺寸：

    SLOT_WIDTH  = 960
    SLOT_HEIGHT = 1080
    IMAGE_WIDTH = 640
    IMAGE_HEIGHT = 480
    PAD_X = (960 - 640) / 2  = 160
    PAD_Y = (1080 - 480) / 2 = 300

对通道索引 k=0..7：

    slot_col = k % 4
    slot_row = k / 4
    slot_x = slot_col * 960
    slot_y = slot_row * 1080
    image_x0 = slot_x + 160
    image_y0 = slot_y + 300
    image_x1 = image_x0 + 639
    image_y1 = image_y0 + 479

满足 image_x0 <= x <= image_x1 且 image_y0 <= y <= image_y1 时，
输出该通道图像像素；否则输出黑色 RGB=0x000000。

## 5. 通道映射

当前 V2.0 系统约定本地视频为 CH0~CH7，HDMI 汇聚视频为 CH8~CH15。

| HDMI 图像索引 | 系统通道 | 槽位列 | 槽位行 | 图像 X 范围 | 图像 Y 范围 |
|---:|---:|---:|---:|---|---|
| 0 | CH8  | 0 | 0 | 160..799   | 300..779   |
| 1 | CH9  | 1 | 0 | 1120..1759 | 300..779   |
| 2 | CH10 | 2 | 0 | 2080..2719 | 300..779   |
| 3 | CH11 | 3 | 0 | 3040..3679 | 300..779   |
| 4 | CH12 | 0 | 1 | 160..799   | 1380..1859 |
| 5 | CH13 | 1 | 1 | 1120..1759 | 1380..1859 |
| 6 | CH14 | 2 | 1 | 2080..2719 | 1380..1859 |
| 7 | CH15 | 3 | 1 | 3040..3679 | 1380..1859 |

槽位内图像坐标转换：

    src_x = x - image_x0
    src_y = y - image_y0

每路恢复后的图像严格为 src_x=0..639、src_y=0..479，不发生缩放、
镜像或旋转。

## 6. 发送端要求

发送端从 8 路最新完整帧生成一个连续 4K transport：

    CH8  latest complete frame --+
    CH9  latest complete frame ---+
    ...                          +-> 4x2 compositor -> HDMI TX
    CH15 latest complete frame --+

在每个 4K transport 帧开始时，一次性锁存 8 路源帧的地址、版本和有效标志。
该 4K 帧输出期间不得更换任一路源帧地址。

规则：

1. 只选择已经完成写入 DDR、状态为 READY 的源帧；
2. 4K SOF 到来时锁存 source_addr[8] 和 source_version[8]；
3. 源帧在该 transport 帧结束前保持引用，不能被写 DMA 复用；
4. 某路没有新的 READY 帧时，继续显示该路上一张稳定帧；
5. 某路从未收到有效帧时，该槽位输出黑色。

发送端按 transport 坐标生成像素。图像区域内读取锁定源帧，其他坐标直接
生成黑色；黑边不得从 DDR 读取。源帧读取不足时应产生诊断计数，并按当前
帧策略输出黑色或保持上一拍，不能让 HDMI AXIS 出现无界停顿。

系统 DDR 中源帧统一按 640x480、XRGB8888、4 bytes/pixel 存储，stride
至少为 2560 bytes。通过 HDMI 发送时丢弃 X 字节，按 RGB888 顺序送入
HDMI 视频 IP。

## 7. 接收端空间拆分

接收端必须在 DDR 写入前完成拆分：

    HDMI RX 3840x2160
            |
            v
    Transport validator / coordinate tracker
            |
            v
    4x2 spatial crop/demux
            |
            +--> CH8  640x480 AXIS
            +--> CH9  640x480 AXIS
            +--> ...
            `--> CH15 640x480 AXIS
            |
            v
    Async FIFO / Stream Normalizer
            |
            v
    Multi-Channel Video DMA

接收端不能把带黑边的 4K 完整帧写入 DDR 再裁剪。

每个拆分输出流为 640x480、RGB888 或转换后的 XRGB8888、2 pixels/clock，
并生成该路独立的 SOF、EOL、EOF。推荐直接输出 48-bit、2 PPC RGB888 AXIS，
再由公共 Stream Normalizer 补 X 字节并附加 stream_id。

transport 计数器只在输入 AXIS 真正接收一拍时推进：

    transport_fire = s_axis_tvalid && s_axis_tready

所有图像区域边界均为偶数，不允许一个 2 PPC beat 跨越图像区域边界。每路
输出每行固定 320 beats、每帧固定 480 行。

## 8. 反压和异常策略

HDMI RX transport 是实时输入，单路输出 FIFO 不能把停顿传播回 HDMI RX。

- HDMI RX 到空间拆分逻辑保持连续排空；
- 每路输出使用独立 FIFO 或等价的有界缓冲；
- 某一路 FIFO 满时，不停住其他通道和 HDMI transport；
- 对该路增加 overflow_count，并将当前源帧标记为丢弃或 malformed；
- transport 继续计数到完整 EOF，保证下一帧重新对齐；
- 不用黑色像素值判断摄像头是否存在，存在性使用 present_mask 或控制寄存器。

建议提供 transport_frame_count、transport_malformed_count、每路
frame_count、overflow_count、malformed_count、last_frame_id，以及
demux_underflow_count。

如果 transport 参数检查失败，接收端应禁止产生有效 CH8~CH15 帧，直到收到
合法的新 transport 配置。

## 9. 帧编号和元数据

HDMI 可见像素不携带 stream_id、源端 frame_id 或 timestamp。第一版规定：

- stream_id 由接收端按空间槽位固定生成：CH8~CH15；
- frame_id 由接收端按每个合法 4K transport 帧递增生成；
- 同一个 4K transport 帧裁出的 8 路流共享同一个 transport frame epoch；
- 原始本地摄像头的 frame_id 不要求透传；
- present_mask、模式状态和错误状态通过本地 MMIO/控制面提供。

如果未来必须透传源端 frame_id，应增加独立元数据通路或明确的 HDMI
InfoFrame/保留行协议，不能把信息编码到有效图像像素中。

## 10. 带宽和验收

8 路源图像按 XRGB8888、30 FPS 写入 DDR：

    8 * 640 * 480 * 4 * 30 = 294,912,000 bytes/s
    约 281.25 MiB/s，不含 AXI 和 DDR 开销

4K HDMI transport 链路像素量：

    3840 * 2160 * 30 = 248,832,000 pixels/s

黑边不应转化为 DDR 视频写流量。接收端只向 DDR 写入 8 个裁剪后的
640x480 流。

仿真至少覆盖：

1. CH8~CH15 纯色映射；
2. 递增坐标图案，验证无镜像、错行、错列和 byte swap；
3. 槽位外全部黑色；
4. 4K 每帧 2160 行、每行 3840 像素；
5. 每路每行 320 个 2 PPC beat；
6. transport 帧中途切换源帧地址时阻止切换；
7. 单路无效或 FIFO 满时不影响其他七路；
8. 错误 transport 不产生假有效帧；
9. 连续至少 120 个 transport 帧无坐标漂移。

硬件验收必须确认 3840x2160p30 RGB 8-bit 2PPC 锁定、CH8~CH15 均有独立
640x480 图像、每路约 30 FPS、无持续 overflow/malformed，且单路停止不
影响 HDMI RX 和其他通道。

## 11. 实现顺序

    第一阶段：4K30 测试图/八路纯色生成器
    第二阶段：4K30 空间拆分仿真
    第三阶段：HDMI RX 接入空间拆分
    第四阶段：CH8~CH15 接入现有八路 DDR 视频 DMA
    第五阶段：发送端从八路真实 DDR 帧生成 4K 汇聚图

在空间封装和拆分通过仿真、ILA 和长时间硬件测试前，不引入缩放、动态布局、
拼接模式切换或源端元数据扩展。

本文件是后续 HDMI 汇聚视频实现的唯一空间布局依据。
