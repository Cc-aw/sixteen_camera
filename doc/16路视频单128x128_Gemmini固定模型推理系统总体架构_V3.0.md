# 16 路视频单 128×128 Gemmini 固定模型推理系统总体架构

> **版本：V3.0**  
> **定位：单大阵列 / 固定模型 / Batch-first Runtime**  
> **目标平台：XCVU13P + Rocket RV64 + Saturn RVV + Single Gemmini 128×128**  
> **视频规模：8 路本地视频 + 8 路 HDMI 汇聚视频，共 16 路 640×480@30 FPS**  
> **模型形态：启动后只运行一个固定模型**  
> **Batch 基线：固定 N=16，NHWC；后续根据 Profiling 再评估动态 Batch 1~16**  
> **Gemmini 目标频率：200 MHz（必须以综合 / Place / Timing 实测为准）**

---

# 1. 版本变化与设计目标

V3.0 不再沿用 V2.0 的 Multi-Gemmini Worker Pool 思路。

V2.0 的主要问题是：

```text
16 路视频
    +
多个并发 AI Frame
    +
Per-Frame Node Progress
    +
Node Ready Queue
    +
Cross-Frame Batcher
    +
Multi-Gemmini Worker Pool
```

该结构适用于：

```text
多个 Gemmini
+
多个 Frame 在不同 Node 上乱序推进
+
Runtime 动态决定 Node -> Device
```

现在硬件约束已经变化为：

```text
Single Gemmini
128 × 128
Fixed Model
```

因此 V3.0 的核心问题不再是：

```text
“任务应该发给哪个 Gemmini？”
```

而变成：

```text
“怎样持续给唯一的 128×128 大阵列提供足够大的有效工作集？”
```

系统优化目标重新定义为：

```text
1. 16 路视频持续稳定采集
2. Capture / Inference 解耦
3. 始终优先处理最新帧
4. 以 Batch16 作为第一版大阵列利用率基线
5. 固定模型采用静态执行计划
6. 权重只保存一份
7. Tensor 地址静态规划
8. 尽可能提高 Weight / Activation 片上复用
9. DMA / Preprocess / Gemmini / Postprocess 流水重叠
10. 完整观测 Array Utilization / DMA Stall / Batch Latency
```

# 4. 架构分层

V3.0 划分为六个逻辑平面：

```text
1. Video Ingress Plane
2. Video Memory Plane
3. Frame / Batch Scheduling Plane
4. Pre/Post Process Plane
5. Fixed Model Execution Plane
6. Memory / Control / Observability Plane
```

其中：

```text
Video Plane
```

负责稳定接收全部视频；

```text
AI Plane
```

只消费当前算力允许处理的最新帧。

二者必须严格解耦。

---

# 5. Video Ingress Plane

## 5.1 输入组成

```text
CH0  ~ CH7   : Local Video ×8
CH8  ~ CH15  : HDMI Aggregated Video ×8
```

每路：

```text
640 × 480 @ 30 FPS
```

总输入：

```text
16 × 30
=
480 Frame/s
```

统一内部视频格式：

```text
XRGB8888
4 Byte / Pixel
```

理论原始写入数据量：

```text
640 × 480 × 4 × 30 × 16
=
589,824,000 Byte/s
≈
590 MB/s
```

该数据量仅代表视频 Frame Store 的连续写流量，不包含：

```text
AI Tensor
Weights
Display Read
Gemmini DMA
Postprocess
```

因此 AI Memory Wall 必须单独观测。

---

## 5.2 Stream Normalizer

所有输入统一转成：

```c
typedef struct {
    uint32_t stream_id;
    uint64_t frame_id;
    uint64_t timestamp;

    bool sof;
    bool eol;
    bool eof;

    bool valid;
    bool error;
} VideoStreamMeta;
```

Normalizer 之后：

```text
DMA
Scheduler
Runtime
```

不再关心视频来自：

```text
Local Camera
或
HDMI Aggregated Camera
```

---

## 5.3 Async FIFO

每路独立 FIFO：

```text
CH0  -> FIFO0
CH1  -> FIFO1
...
CH15 -> FIFO15
```

职责：

```text
Clock Domain Crossing
Burst Aggregation
Traffic Buffering
Input Jitter Isolation
Short-term Backpressure Absorption
```

FIFO 不承担完整帧缓存。

---

# 6. Video Memory Plane

## 6.1 Multi-Channel Video DMA

继续采用：

```text
16 Stream Context
+
少量共享 AXI Write Engine
```

推荐第一版：

```text
16 Stream Context
+
2 AXI Write Engines
```

而不是：

```text
16 Stream
=
16 AXI Master
```

DMA 仲裁考虑：

```text
FIFO Watermark
Burst Length
Age
Deadline
Per-stream Credit
AXI Outstanding
QoS
```

目标：

```text
高 AXI Efficiency
无长期 Starvation
无持续 FIFO Overflow
单路异常不影响其他通道
```

---

## 6.2 DDR Frame Store

每路继续使用 Triple Buffer：

```text
CH0  : F0 F1 F2
CH1  : F0 F1 F2
...
CH15 : F0 F1 F2
```

Frame Buffer 元数据：

```c
typedef struct {
    uint32_t stream_id;
    uint64_t frame_id;
    uint64_t timestamp;

    uintptr_t addr;

    uint32_t version;
    uint32_t refcount;
    uint32_t state;
} FrameBufferMeta;
```

只有满足：

```text
refcount == 0
且
不再作为当前 Latest Frame
```

时才能被 Video DMA 重用。

---

## 6.3 Latest Frame Table

每个 Stream 对 AI 只暴露最新稳定帧：

```c
typedef struct {
    uint32_t stream_id;

    uint64_t frame_id;
    uint64_t timestamp;

    uintptr_t frame_addr;

    uint32_t version;

    bool valid;
    bool error;
} LatestFrameEntry;
```

AI 不维护无限历史帧队列。

原则：

```text
New Frame
覆盖
Old AI Candidate
```

而不是：

```text
Camera
-> Frame Queue
-> Frame Queue
-> Frame Queue
-> AI
```

# 7. Capture / Inference 解耦

Video Plane：

```text
固定接收：
16 × 30 FPS
=
480 FPS
```

Inference Plane：

```text
实际 AI FPS
由
Gemmini + DDR + Preprocess + Postprocess
实测吞吐决定
```

不能因为 AI 变慢就：

```text
反压 Camera
```

AI 过载时只允许：

```text
Frame Supersede
Frame Skip
Frame Drop
```

因此：

```text
Capture FPS != Inference FPS
```

这是 V3.0 仍然必须保留的系统原则。

# 8. Frame / Batch Scheduling Plane

V3.0 不再保留：

```text
Frame Scheduler
+
Node Scheduler
+
Batch Candidate Scheduler
+
Worker Scheduler
```

而简化成：

```text
Frame Snapshot Scheduler
+
Batch16 Builder
```

# 9. Frame Snapshot Scheduler

Scheduler 的职责只有一个：

```text
为下一次 Batch 选择每一路当前最新的稳定帧
```

第一版采用静态槽位：

```text
Batch Slot0  <-> CH0
Batch Slot1  <-> CH1
...
Batch Slot15 <-> CH15
```

每次 Batch 构建时：

```text
读取 LatestFrameTable[0..15]
```

并生成一个一致的 Frame Snapshot。

注意：

```text
CH0 Frame 105
CH1 Frame 103
CH2 Frame 108
...
```

完全允许。

系统不要求 16 路视频拥有相同：

```text
frame_id
timestamp
SOF 时间
```

Batch 仅表示：

```text
“当前这一轮一起进行 AI 推理的 16 个输入样本”
```

而不是：

```text
“严格同步采样的同一时刻帧”
```

# 10. Batch16 Baseline

## 10.1 第一版固定 N=16

P0 / P1 的主要性能基线：

```text
N = 16
```

模型输入：

```text
NHWC
```

即：

```text
[16][H][W][C]
```

例如如果固定模型输入为：

```text
416 × 416 × 3
```

则：

```text
[16][416][416][3]
```

如果未来模型输入尺寸变化，只重新生成固定模型配置，不改变 Runtime 架构。

---

## 10.2 为什么先固定 Batch16

Batch16 在第一版不是因为：

```text
16 一定是理论最优 Batch
```

而是因为：

```text
16 Streams
        ↓
每路提供一个最新 Frame
        ↓
天然形成 16 Sample
```

其工程优势：

```text
1. Tensor Shape 固定
2. Slot -> Stream 映射固定
3. 软件最简单
4. 最容易验证 NHWC Batch 正确性
5. 同一层 Weight 天然被 16 个 Sample 复用
6. 可以快速验证 128×128 大阵列是否真的受益于 Batch
```

后续 Profiling 才决定是否需要：

```text
B = 1 / 2 / 3 / ... / 16
```

动态变化。

---

# 11. Batch Valid / Fresh Mask

固定 N=16 不代表必须等待 16 路全部产生新帧。

BatchContext 保存：

```text
valid_mask
fresh_mask
```

定义：

```text
valid_mask[i] = 1
```

表示：

```text
Slot i 有可用于推理的稳定 Frame
```

```text
fresh_mask[i] = 1
```

表示：

```text
Slot i 相比上一轮 Batch 获取了新的 frame_id
```

对于暂时没有新帧的 Stream：

优先策略：

```text
仍使用 Latest Stable Frame
```

但：

```text
fresh_mask[i] = 0
```

如果 Stream 从未产生有效帧：

```text
valid_mask[i] = 0
```

该 Slot 使用预定义填充值：

```text
Zero / Black Tensor
```

最终 Postprocess 忽略该 Slot 结果。

原则：

```text
任何单路 Camera 异常
都不能阻塞整个 Batch16
```

```c
    uint32_t state;

```

P0：

```text
batch_size = 16
```

固定不变。

# 14. Preprocess Plane

数据路径：

```text
DDR Frame Store
        |
        v
    S01 / S02
        |
        v
Preprocess / Saturn RVV
        |
        v
NHWC Batch Input Tensor
        |
        v
Coherent Tensor Memory
```

原则：

```text
Video Full Frame
-> Bypass Rocket Cache

AI Tensor
-> Coherent Memory

Control / Metadata
-> Rocket Cached Memory
```

Preprocess 对 16 个 Slot 做：

```text
Resize
Color Convert
Normalization / Quantization
Layout
Padding
```

最终直接生成固定模型需要的：

```text
NHWC Batch Tensor
```

避免：

```text
16 个独立 HWC Tensor
        ↓
再额外拼接一次 Batch
```

理想路径：

```text
16 Frame
   ↓
Preprocess
   ↓
直接写入
[N][H][W][C]
```

启动时不做：

```text

Dynamic Node Binding

```

而直接使用：

```text
Static Model Table
```

执行逻辑：

```text
Layer0
  |
Layer1
  |
Layer2
  |
...
  |
LayerN
```

如果存在：

```text
Residual
Concat
Branch
```

这些依赖关系仍然由：

```text
Static Model Table
+

```

表达。

Runtime 不需要运行期求图依赖。

# 20. Batch 对 128×128 的作用

卷积可近似映射为：

```text
[M, K] × [K, N]
```

其中：

```text
M = Batch × Hout × Wout

K = Kh × Kw × Cin

N = Cout
```

因此：

```text
增大 Batch
主要扩大 M 维
```

Batch 可以改善：

```text
M 方向 Tile 尾块利用率
Weight 跨 Sample 复用
Command / Setup Amortization
DDR Weight Traffic / Frame
```

但不能解决：

```text
N = Cout 太小
```

例如：

```text
Cout = 32
```

对于：

```text
128 列
```

列方向理论最大有效率仍只有约：

```text
32 / 128
=
25%
```

因此 V3.0 必须增加：

```text
Per-Layer Array Utilization Profiling
```

不能只看：

```text
Batch Size
```

# 21. Static Tensor Memory Plan


因此所有 Tensor 地址都应离线规划。

```text

+

```

执行时：

```text
tensor_addr =
batch_arena_base
+
tensor_desc[tensor_id].offset
```


# 26. Weight Residency

单 128×128 Gemmini 的核心优化之一：

```text
同一 Layer Weight
尽可能服务整个 Batch16
```

理想顺序：

```text
Load Weight K
     |
     v
Process Batch Slot0
Process Batch Slot1
...
Process Batch Slot15
     |
     v
Switch Next Weight / Tile
```

实际是否能够完整驻留取决于：

```text
SPAD Size
Weight Tile Size
K Dimension
Layer Shape
```

因此必须记录：

```text
Weight Reload Ratio
```

# 27. SPAD / ACC 设计原则

128×128 INT8 基本矩阵 Tile：

```text
A:
128 × 128 × 1 Byte
=
16 KiB

B:
128 × 128 × 1 Byte
=
16 KiB
```

INT32 Accumulator：

```text
128 × 128 × 4 Byte
=
64 KiB
```

如果做：

```text
A Ping/Pong
B Ping/Pong
```

仅输入双缓冲就需要：

```text
64 KiB
```

还没有包括：

```text
更大 K Tile
Output
Accumulator
Weight Residency
DMA Overlap
Metadata
```

因此 128×128 Gemmini 不应继续沿用小阵列的片上存储配置。

# 28. Weight / Activation Double Buffer

目标执行：

```text

        ||
Load Tile N+1
```

而不是：

```text

  ↓
Wait
  ↓
Compute
  ↓
Wait
  ↓

```

```text

SPAD Bank B
```

轮换：

```text

    ↓

```


# 29. Batch Pipeline

第一阶段：

```text
Batch A

Preprocess
    |
Compute
    |
Postprocess
```

稳定后升级为：

```text
Batch N+1
Preprocess
      ||
Batch N
Gemmini Compute
      ||
Batch N-1
Postprocess
```

即：

```text
       Stage0          Stage1          Stage2

N+1  Preprocess
N                    Gemmini
N-1                                  Postprocess
```

这样单 Gemmini 系统的主要并行来自：

```text
DMA / RVV / Gemmini
```

之间的流水，而不是多个 Gemmini 并行。

---

# 30. 双 Batch Arena

为支持上述流水：

```text
Arena A
Arena B
```

推荐状态：

```text
时间 T0:
A = Compute
B = Preprocess

时间 T1:
B = Compute
A = Preprocess
```

如果 Postprocess 需要更长生命周期，可增加：

```text
Output Ring
```

而不是增加第三套完整 Activation Arena。

# 35. Frame Drop / Supersede

由于：

```text

```

而 AI 可能低于：





不需要显式排队后逐一 Drop。

# 44. 128×128 主要硬件风险

## 44.1 PE 数量

```text
128 × 128
=
16384 PE
```

相比：

```text
64 × 64
=
4096 PE
```

PE 数量增加：

```text
4 ×
```

不能简单认为：

```text
所有资源一定严格 4×
```

但：

```text
Routing
Local Interconnect
Accumulator Access
Broadcast / Fanout
```

压力会明显增加。

---

## 44.2 SLR

VU13P 属于大型多 SLR FPGA。

128×128 大阵列可能出现：

```text
单阵列跨多个 SLR
```

问题包括：

```text
Long Route
High Fanout
Inter-SLR Delay
Placement Congestion
Clock / Reset Distribution
```

因此必须重点观察：

```text
PE Mesh Physical Distribution
SPAD Placement
ACC Placement
DMA Interface Placement
```

---

## 44.3 Memory Wall

大阵列峰值计算能力提升后：

```text
DDR
DMA
SPAD
```

更容易成为瓶颈。

如果：

```text
Array Idle
```

原因可能并不是：

```text
模型算得太少
```

而是：

```text
数据没有及时送到阵列
```

V3.0 最重要的五个指标：

```text
1. End-to-End FPS
2. Gemmini Array Utilization
3. DMA Stall Ratio
4. Weight Traffic / Frame
5. Batch End-to-End Latency
```

这五个指标比：

```text
Queue 数量
Worker 数量
Scheduler 复杂度
```

更重要。


# 69. 当前架构真正需要解决的问题

V3.0 的核心问题压缩成四个：

```text
问题一：
128×128 Gemmini 能否在 VU13P 上资源 / 时序收敛？

问题二：
固定模型的各 Layer 是否能有效利用 128×128？

问题三：
Batch16 是否能显著提高大阵列利用率和 Weight Reuse？

问题四：
DDR / DMA / SPAD 是否会成为新的主瓶颈？
```

Runtime 设计必须围绕这四个问题服务。

系统不再回答：


```text

```

# 72. 最终设计原则

```text
先证明硬件可实现
再证明模型正确
再证明 Batch 有收益
再优化 Memory Wall
最后才增加 Runtime 复杂度
```

V3.0 的设计目标不是：

```text
做一个最通用的 AI Runtime
```

而是：

```text
用最确定、最静态、最容易优化的方式，
把一个固定模型在单个 128×128 Gemmini 上跑到尽可能高的真实利用率。
```
